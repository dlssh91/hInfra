# 취약점 평가 LLM 자동 판단 도구 — 설계 문서

- 작성일: 2026-06-01
- 상태: 설계 확정 (구현 1단계 = 클라우드 AWS)

## 1. 배경 / 목적

전자금융기반시설 보안 취약점 평가에서, 점검 스크립트가 생성한 결과물(클라우드 XML, DB
점검 txt 등)을 평가자가 직접 읽고 평가기준의 **판단기준**과 대조해 항목별 **양호/취약**을
판정한다. 이 작업은 항목·리소스가 많아 시간이 많이 소요된다.

본 도구는 **로컬 LLM(Ollama)** 을 사용해 "스크립트 결과 + 해당 항목 판단기준"으로 항목별
판정 초안을 자동 생성한다. 평가자는 초안을 검토·확정한다.

### 로컬 LLM 필수 사유
점검 결과물에는 민감정보가 그대로 포함된다(예: Oracle 결과 내 비밀번호 해시). 따라서
데이터가 단말 밖으로 나가면 안 되며, 외부 API가 아닌 **로컬 처리**가 필수다.

## 2. 범위

### 대상 평가기준 (ref/ 내 xlsx, 제2026-1호)
최종 목표는 다음 분야 전체 자동화:
클라우드 관리체계 / 서버 / 데이터베이스 / 네트워크 장비 / 정보보호시스템 장비 /
OS 가상화 시스템 / 컨테이너 가상화 시스템.

### 전 분야 공통 데이터 모델 (실측 확인)
모든 시트가 동일 골격을 공유한다:
`항목 × 변형(variant) × (판단기준, 판단방법, 평가대상)`.
- 항목 ID 체계는 분야별로 다름: PISM / DBM / SRV / NET / ISS / PRCV / PRCC.
- 변형: 클라우드=AWS·Azure, 서버=OS별, DB=DBMS×플랫폼(~15), 컨테이너=오케스트레이터×노드 등.
- 결과파일 키 = xlsx 평가항목ID에 대응. 분할 항목(`DBM-004_1/2/3`, `pism_045_1/2/3`)은
  하나의 상위 항목으로 집계.
- 변형은 파일명/경로로 식별 가능(`aws_report_*`, `oracle_result_rds.txt`).

### 증거(입력) 스타일 — 두 종류 (중요)
| | 클라우드 XML | DB txt (및 다수 분야 추정) |
|---|---|---|
| 1차 판정 | 스크립트가 status `good/bad/info/error` 부여 | 없음 — 원시 쿼리/명령 결과만 |
| 파싱 | 표준 XML | 비표준 JSON(백틱, trailing comma) → 관대한 파싱 필요 |
| LLM 부담 | 집계·확인 | 원시 데이터→판단기준 대조 |

→ "원시 증거"가 일반 케이스, 클라우드(사전분류)가 특수 케이스. LLM은 두 경우 모두 판단 가능해야 함.

### 구현 단계
- **1단계(본 spec 구현 대상): 클라우드(AWS) 한 분야.**
- 이후: Azure(동일 XML, 프로파일 variant만 추가) → DB/서버 등(증거 파서 플러그인 추가).
- 분야 추가 = "프로파일(시트 컬럼맵 + 증거 파서 + variant 규칙)" 작성. 코어는 재사용.

## 3. 핵심 설계 결정

1. **항목별 개별 LLM 호출 (A안).** 항목 1개당 호출 1회, 그 항목의 판단기준+증거만 입력.
   긴 컨텍스트에서의 로컬 모델 정확도 저하를 회피, 항목별 확신도 산출, 부분 실패 격리.
2. **LLM 독립 판단 + 스크립트 교차 비교.** 스크립트의 good/bad를 정답으로 신뢰하지 않고,
   LLM이 판단기준 기준으로 독립 판정한 뒤 스크립트 status와 비교한다.
   - 일치 → 확신도↑
   - 불일치 → `needs_review = true`("재검토 필요")
   - 이 신호가 1단계(검토 초안) → 최종 3단계(확신도 기반 자동확정)로 가는 다리.
   - 부수효과: 클라우드도 DB와 동일한 "원시 증거 → LLM 판단" 경로를 사용 → 코어 통일.
3. **코어/프로파일 분리(경량).** 프로파일은 무거운 플러그인 프레임워크가 아니라 작은
   설정 객체(dataclass/dict). 이음새만 깨끗이.
4. **판단기준은 xlsx에서 런타임 추출.** 코드 하드코딩 금지 → 기준 개정 시 자동 반영.
5. **출력은 JSON(머신용) + Excel 별도 보고서(평가자용).** 공식 xlsx에 써넣지 않음(안전).
6. **모델은 설정으로 교체 가능.** 기본값은 추후 "최저 사양 대비 결과 일관성" 실측 후 결정.

## 4. 아키텍처

```
result 파일 (XML/txt)  +  평가기준 xlsx
        │
   [evidence parser]    ← 분야별 플러그인. 정규화 출력:
        │                 {item_id, variant, raw_evidence, script_status?}
   [criteria loader]    ← xlsx → {item_id, variant} → 판단기준/판단방법/위험도
        │
   [mapper]             ← ID 정규화(pism_001→PISM-001), 분할항목 집계, 파일명→variant
        │
   [judge]              ← 항목별 Ollama 호출 (localhost:11434, 온도 0)
        │                 입력: 판단기준(기술/스크립트 섹션) + 판단방법 + 증거
        │                 출력: verdict + confidence + rationale + 인용 (JSON 강제)
        │
   [reconcile (함수)]   ← LLM verdict ↔ script_status 비교, needs_review 산정
        │
   [writer]             → result_*.json  +  result_*.xlsx  + 커버리지 요약
```

### 컴포넌트 (단일 책임)
| 모듈 | 책임 |
|---|---|
| `criteria_loader.py` | xlsx → 항목×변형별 판단기준/판단방법/위험도/평가구분 |
| `parsers/cloud_xml.py` | 클라우드 XML → 정규화 증거(script_status 포함) |
| `mapper.py` | ID 매핑·분할항목 집계·파일명→variant·N/A 변형 스킵 |
| `judge.py` | 프롬프트 생성 + Ollama 호출 + 응답 스키마 검증·재시도 + reconcile 함수 |
| `writer.py` | JSON + Excel + 커버리지 요약 출력 |
| `profile.py` | 분야 설정 객체(시트명, 컬럼맵, 파서 선택, variant 규칙) — 경량 |
| `main.py` | CLI 오케스트레이션 |

(`comparator`는 별도 모듈로 분리하지 않고 judge 내 함수로 흡수.)

## 5. 판정 출력 스키마 (항목당)

```json
{
  "item_id": "PISM-001",
  "item_name": "통신구간 암호화 적용 여부",
  "variant": "AWS",
  "risk": 5.0,
  "verdict": "취약",                 // 양호 | 취약 | 판단보류
  "confidence": 0.86,
  "rationale": "버킷 X에 SecureTransport=false 거부 정책 부재 ...",
  "cited_evidence": ["bucket-A: 버킷 정책 미존재"],
  "scope": "스크립트 전체",          // "스크립트 전체" | "스크립트 부분만"
  "management_review_needed": false, // 관리체계 혼합 항목이면 true
  "script_status": "bad",            // 비교용, 없으면 null
  "agreement": "일치",               // 일치 | 불일치 | N/A
  "needs_review": false              // 불일치 또는 confidence 낮음 또는 부분판정이면 true
}
```

### 감사(audit) 메타데이터 (보고서 헤더)
`사용 모델명/버전`, `기준 파일명(제2026-1호)`, `실행 시각`, `입력 파일 해시`, `도구 버전`.
→ "이 판정이 무엇으로 산출됐는지" 사후 방어 가능.

## 6. 세부 규칙

### 6.1 분할항목 집계 (holistic)
`045_1/2/3`처럼 하위로 나뉜 결과는 **하위 증거 전체를 한 번의 LLM 호출에 넣고**, xlsx의
**단일 판단기준**으로 **하나의 verdict**를 낸다. (xlsx 판단기준이 항목당 1개뿐이므로 이 방식이 정합.)

### 6.2 "관리체계 + 스크립트" 혼합 항목 = 부분 판정
클라우드의 PISM-007/013/023/037/039/045 등 평가구분이 `관리체계, 스크립트`인 항목은
판단기준에 `[관리체계]`(문서·인터뷰)와 `[IAM]/[Lambda]…`(스크립트) 섹션이 공존한다.
- 본 도구는 **스크립트 근거가 있는 부분만** 판단한다.
- 프롬프트는 판단기준 중 **기술/스크립트 섹션만 대조**하도록 지시.
- 출력에 `scope="스크립트 부분만"`, `management_review_needed=true` 표기.

### 6.3 증거 크기 가드 (취약 후보 우선 보존)
로컬 모델 컨텍스트 보호를 위해 항목별 증거 길이 상한을 둔다. 단순 head 절단 금지.
- 클라우드: `status≠good`(bad/error/info)인 Item을 **전량 보존**, good만 샘플링·축약.
- 원시(DB 등): 행 상한 적용 시 **"N행 중 일부 표시"** 명시 → LLM이 불완전성 인지.

### 6.4 N/A 변형 스킵
해당 variant의 판단기준이 비어있거나 평가구분이 `N/A`면 그 항목은 "해당없음"으로 스킵.

### 6.5 커버리지 리포트
보고서 상단에 `판정 N / 대상 M`, `미판정 항목 목록`(증거 없음/시트 미존재) 요약.

### 6.6 결과 일관성 장치
온도 0, JSON 스키마 강제(+실패 시 1~2회 재시도), 항목별 소컨텍스트, (지원 시) seed 고정.
스크립트 비교가 일관성 흔들림의 안전망.

### 6.7 에러 처리
- 증거 없음/`error` status → `판단보류`.
- Ollama 연결 실패 → 명확한 안내 후 중단.
- 비표준 JSON(원시) → 관대한 전처리(백틱→따옴표, trailing comma 제거).

## 7. 테스트 전략
- 골든 테스트: 업로드된 실제 샘플 `results/Public Cloud/aws_report_*.xml`로 end-to-end.
- 단위 테스트: parser/mapper/criteria_loader/reconcile는 순수 로직 → 단위 테스트.
- judge: Ollama 응답 모킹으로 프롬프트 구성·스키마 검증·재시도 경로 테스트.

## 8. 향후 단계 (1단계 차단요소 아님, 기록용)
- **정확도 기준선 측정**: 최종 3단계(자동확정)로 가기 전, 소규모 사람-라벨 정답셋과
  LLM 판정의 일치율을 측정해야 안전하다. 클라우드는 script 비교가 한 신호를 주지만
  원시증거 분야(DB 등)는 신호가 없으므로 골든셋 라벨이 필요.
- 확신도 임계값 정의 → `needs_review` 자동 분기로 3단계 전환.
- 분야 확장: Azure → DB → 서버 → 네트워크 → 정보보호 → 가상화(프로파일/파서 추가).

## 9. 기술 스택
Python 3, Ollama HTTP API(localhost:11434), 의존성 최소화(`requests`, `openpyxl`).
출력 한국어.
